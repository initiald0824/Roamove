# 多地图内容契约与存档边界示例

日期：2026-11-17。状态：静态内容设计与引用核对，尚未实现加载器或 App 引擎。

## 本轮把原则变成什么

提供三份可解析的数据示例：

- [共用能力、训练模板与物品](examples/shared-content.json)。
- [鳌太线结构样例](examples/aotai-demo.route.json)：3 个节点、2 条行程，包含巧克力选择与营地煮面。
- [虚构海岸结构样例](examples/coast-fiction.route.json)：5 个节点、6 条行程，包含分岔、汇合与回访，使用同一批共用能力。

这些 JSON 是内容契约讨论样例，所有 `executionReady` 都为 `false`。鳌太线样例的现实连接尚未核实，海岸线完全虚构，只用来检验内容组织，不是第二张地图的上线提案。

示例只列出必要库存和故事标记，没有完整定义角色体力恢复、昼夜演出或课程剂量规则；这些能力需要后续各自的内容与实现，不能从几个示例字段推定已经具备。

## 共同约定

路线用稳定 `routeId`，各自保存 `contentVersion`。节点、行程与事件标识归属当前路线，显示名称按语言保存；不能依赖“第几关”或中文地名作为全局主键。

路线引用共用训练模板和动作目录，训练模板再引用动作 ID。地图描述行程与事件，不直接覆盖个人活动限制、负荷或医学判断。共用模板的版本、课程适用范围与动作识别状态独立管理。

每份地图显式指定 `sharedContentVersion`，避免“动作 ID 没变但其定义已经被新版本覆盖”。本例先固定共用内容包版本；真正开始训练时还需保存本次计划的版本或快照，不能在用户暂停期间静默换成新的动作与剂量。

物品属于游戏资源，与用户现实训练器材分开。例如防潮垫是角色装备，不能自动当作用户已经备好的运动垫。角色库存、时间和状态也不影响实际活动记录的真实性。

静态内容表达已支持的条件、选择和效果，不包含下载执行的任意程序。新事件类型或新的识别能力需要 App 能力更新，不能只在内容包里填写一个陌生字段就宣称支持。

## 两张地图如何不同

| 项目 | 鳌太线样例 | 虚构海岸样例 |
| --- | --- | --- |
| 节点／行程 | 3／2 | 5／6 |
| 地理状态 | 真实题材，样例连线待核实 | 虚构结构验证用途 |
| 露营 | 声明需要 `event.camp`，引用默认装备 | 没有该能力依赖，也没有露营装备 |
| 食物 | 具体饼干、巧克力、泡面和水 | 仅用水演示资源子集 |
| 结构 | 到站、营地选择与叙事收尾 | 两路汇合、回访和叙事收尾 |
| 训练 | 引用 3 个研究模板 | 复用同一批研究模板 |

因此新地图可以复用现有规则，同时选择不同玩法组合和节点数量。示例只能说明数据表达可以这样组织，不能证明尚未编写的程序已具备可扩展性。

## 更新与保存需要记录什么

建议保存路线 ID、内容与共用包版本、本次远征 ID、所在节点或行程、已确认阶段、事件选择收据、游戏库存和角色状态。本次个人训练计划及实际运动记录独立保存，明确计划版本、所属活动及数据来源。

“确认入关后吃一份路餐”等变化对应唯一收据，同次确认不能因返回、重试或恢复而重复扣除。示例提供 `receiptKey` 表达这个需要，尚未实现去重与事务。

内容升级时，进行中的关卡继续引用原版本；在安全边界检查兼容与迁移后再切换。节点被删除时需要显式映射或保留旧版本，不能只用新数组下标覆盖旧位置。删除素材缓存与删除用户记录分别操作。

## 健康资料与游戏存档分开

用户目标、活动限制、当天状态和训练恢复资料由共用个人训练部分处理。路线内容不包含真实用户健康资料，两个示例也没有采集任何真实个人数据。

本地个人资料、实际运动记录、可同步的游戏进度与素材缓存需要明确分层。Apple 的健康隐私规则对个人健康信息在 iCloud 的存储有限制，不能将整个健康档案默认交给 CloudKit；具体哪些字段可同步及备份策略仍需专门审阅。[App Review Guidelines 5.1.3](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research)

## 本轮结构核对范围

已检查 JSON 能否解析、ID 唯一、节点与行程引用、训练模板与动作引用、物品与素材引用、能力依赖，以及从起点能否到达各节点。两个样例通过本次静态核对，具体结果与未覆盖范围见[核对记录](validation-notes.md)。

不将结构核对写成动作识别、课程适用性、下载器、暂停恢复或存档迁移的运行测试。上述行为需要实现后通过对应测试证明。
